# UI 测试用例规划

## 场景说明
为 iOS 应用模块生成结构化的 UI 自动化测试计划，覆盖核心用户流程、边界条件和错误场景，输出 Given-When-Then 格式用例和所需的 Accessibility Identifier 清单。

## 输入要求

### 必需
- 目标模块名称（如：登录模块、购物车流程）
- 主要页面和功能描述
- 技术栈（UIKit / SwiftUI）

### 可选
- 现有业务需求文档或用户故事
- 已知的边界条件或特殊场景
- 现有测试覆盖情况（避免重复）

## 提示词模板

```
我需要为 iOS 应用的 [模块名称] 规划 UI 自动化测试用例。

## 应用信息
- **模块**：[如：用户登录与注册]
- **技术栈**：[UIKit / SwiftUI]
- **主要页面**：
  1. [页面名称 1]：[功能描述]
  2. [页面名称 2]：[功能描述]
  ...

## 业务场景（可选）
[粘贴业务需求或用户故事]

## 测试目标
- 覆盖核心用户路径（Happy Path）
- 包含错误处理场景（网络失败、无效输入、权限拒绝）
- 验证关键状态转换（如：未登录 → 已登录、空购物车 → 有商品）
- 边界条件（极长输入、特殊字符、多语言）

## 输出要求

### 1. 测试用例清单
按优先级分组（P0 核心流程、P1 重要场景、P2 边界情况），每个用例包含：
- **用例名称**：简洁描述场景
- **优先级**：P0 / P1 / P2
- **Given-When-Then**：结构化描述
- **前置条件**：需要的应用状态（如已登录、网络 Mock 状态）
- **验证点**：具体断言的元素或状态

### 2. Accessibility Identifier 清单
列出所有需要添加的可达性标识符，格式：`<模块>_<组件>_<用途>`

### 3. 测试数据需求
列出需要准备的测试数据（有效/无效用户名、商品 ID 等）

## 示例输出格式

### 用户流程 1：成功登录
- **优先级**：P0（核心流程，必须通过）
- **Given**：用户未登录，在登录页面
- **When**：输入有效的用户名 "testuser" 和密码 "Test1234"，点击"登录"按钮
- **Then**：成功跳转到首页，顶部显示用户头像和昵称 "测试用户"
- **前置条件**：
  - 应用首次启动或已退出登录
  - Mock 网络返回成功响应
- **验证点**：
  - 首页用户头像图片存在
  - 昵称文本为 "测试用户"
  - 登录按钮不再可见

**所需 Accessibility Identifier**：
- `login_textfield_username`（登录页用户名输入框）
- `login_textfield_password`（登录页密码输入框）
- `login_button_submit`（登录页提交按钮）
- `home_image_avatar`（首页用户头像）
- `home_label_nickname`（首页用户昵称）

**测试数据**：
- 有效用户名：testuser
- 有效密码：Test1234

---

### 用户流程 2：密码错误提示
- **优先级**：P1（重要错误处理）
- **Given**：用户未登录，在登录页面
- **When**：输入用户名 "testuser"，输入错误密码 "wrong"，点击"登录"按钮
- **Then**：停留在登录页，显示错误提示 "用户名或密码错误"
- **前置条件**：
  - Mock 网络返回 401 错误
- **验证点**：
  - 错误提示文本内容准确
  - 输入框内容未清空（用户可重新输入）
  - 登录按钮仍可点击

**所需 Accessibility Identifier**：
- `login_label_errorMessage`（错误提示 Label）

**测试数据**：
- 无效密码：wrong
```

## 使用示例

### 输入

```
我需要为 iOS 应用的用户登录模块规划 UI 自动化测试用例。

## 应用信息
- **模块**：用户登录
- **技术栈**：UIKit
- **主要页面**：
  1. 登录页：包含用户名、密码输入框和登录按钮
  2. 首页：登录成功后展示用户信息和商品列表

## 测试目标
- 覆盖正常登录流程
- 覆盖密码错误、网络失败等异常场景
- 验证登录状态持久化
```

### AI 输出（部分）

**（会生成完整的测试计划，包含多个用例、所需标识符和测试数据清单）**

## 注意事项

### ✅ 好的做法
- **明确优先级**：P0 用例应覆盖最核心的用户路径，失败即阻塞发版
- **验证点具体**：不只说"登录成功"，明确列出要验证的元素（头像、昵称等）
- **标识符命名统一**：全部采用 `模块_组件_用途` 格式，便于维护
- **考虑前置条件**：明确测试需要的应用状态和 Mock 配置

### ❌ 避免的做法
- 过于宏观的用例描述（如"测试登录功能"），缺少操作细节
- 忽略边界条件（极长输入、特殊字符、多语言切换）
- 验证点模糊（"页面正常显示"），无法转化为具体断言
- 标识符命名混乱（有的用驼峰，有的用下划线）

### 🔧 常见调整

如果 AI 生成的测试计划不符合预期，可以追加指令：

```
请调整以下内容：
1. 补充 P2 边界条件用例：用户名包含特殊字符、密码长度超过 100 字符
2. 为每个用例添加"预期执行时间"（用于评估测试套件总耗时）
3. 标注哪些用例需要 Mock 网络（避免依赖真实后端）
4. 将表格导出为 CSV 格式（便于导入测试管理系统）
```

## 高级用法

### 场景一：多语言测试用例
```
额外要求：
- 为核心 P0 用例生成英文、简体中文、繁体中文三个版本
- 验证点需检查本地化文本是否正确
```

### 场景二：权限相关测试
```
应用信息补充：
- 需要相机、定位、通知权限
- 用户首次使用时会弹出系统权限请求

测试目标：
- 覆盖授权/拒绝权限后的应用行为
- 验证设置中权限引导提示
```

### 场景三：回归测试用例
```
额外输入：
- 历史 bug 列表（bug ID、现象、根因）

输出要求：
- 为每个已修复的 bug 生成对应的回归测试用例
- 用例描述中引用 bug ID
```
